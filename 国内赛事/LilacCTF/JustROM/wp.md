# JustROM - CTF逆向题目 Writeup

## 题目信息
- 题目名称：Just a randomly picked ROM
- Flag格式：LilacCTF{...}
- 文件：rom.bin (81920 字节 = 0x14000)

## 分析过程

### 1. 初步分析

首先查看ROM文件的十六进制内容：

```
00000000: 1080 1000 0100 0000 0100 0000 0100 0000  ................
00000010: 1080 0ffc 0100 0000 0100 0000 0100 0000  ................
...
```

文件开头有规律的 `1080 xxxx` 模式重复出现，后面跟着 `0100 0000`（nop指令）。

### 2. 架构识别

在 0x4000 偏移处发现了典型的SPARC指令：
- `9de3 bfa0` - `save` 指令（函数入口）
- `81e8 0000` - `restore` 指令
- `81c3 e008` - `retl` 指令（从叶子函数返回）

**确认架构：SPARC (大端)**

### 3. ROM结构分析

| 偏移范围 | 内容 |
|---------|------|
| 0x0000 - 0x0FFF | 跳转表（SPARC分支指令） |
| 0x1000 - 0x3FFF | 加密数据区 |
| 0x4000 - 0x4FFF | SPARC可执行代码 |
| 0x5000 - 0xBFFF | 空白区域（全0） |
| 0xC000 - 0xC02F | 密钥和Nonce数据 |

### 4. 发现ChaCha20加密

在 0x4018 处发现了 ChaCha20 的特征常量：
```
00004018: 6170 7865 3320 646e 7962 2d32 6b20 6574  apxe3 dnyb-2k et
```

这是 "expand 32-byte k" 按每4字节反转后的存储形式，是 ChaCha20/Salsa20 算法的标准常量。

### 5. 密钥和Nonce位置

在 0xC000 处发现密钥和Nonce：

```
0000c000: 1122 3344 5566 7788 99aa bbcc ddee ff00  ."3DUfw.........
0000c010: dead beef cafe babe 0bad f00d 1337 1337  .............7.7
0000c020: 4141 4141 4242 4242 4343 4343 0000 0000  AAAABBBBCCCC....
```

- **密钥 (32字节)**：`112233445566778899aabbccddeeff00deadbeefcafebabe0badf00d13371337`
- **Nonce (12字节)**：`AAAABBBBCCCC` (ASCII: 0x41414141, 0x42424242, 0x43434343)

### 6. SPARC代码反汇编

#### ChaCha20 状态初始化 (0x4090)

代码从以下地址加载数据构建 ChaCha20 状态：
- `0x40008018-0x40008024`：ChaCha20 常量
- `0x40010000-0x4001001C`：32字节密钥
- Counter = 1
- Nonce = 0x41414141, 0x42424242, 0x43434343

#### 字符串常量

在代码中发现构造的字符串：
```
"There_is_nothing_you_wanna_get.."
"NOEL"
```

这些通过 `sethi` + `or` 指令对构造：
```sparc
sethi 0x151a19, %r28    ; 0x54686400
or %r28, 0x172, %r28    ; = 0x54686572 = "Ther"
```

### 7. 字节码解释器

在 0x4D00 处发现了一个字节码解释器，读取 0x42000200 处的字节并执行操作：

| 字节码 | 操作 |
|--------|------|
| 0x10 | 重置计数器为0 |
| 0x11 | 计数器+1 |
| 0x22 | 计数器-1 |
| 0x33 | 将当前位置字节设为0 |
| 0x44 | 将当前位置字节+1 |
| 0x55 | 将当前位置字节*2 |
| 0xEE | 调用验证函数 (0x4AB0) |

### 8. 验证函数分析 (0x4AB0)

验证函数构造 "There_is_nothing_you_wanna_get.." 字符串，然后与一组加密常量进行 XOR 操作：

### 9. 地址映射

SPARC代码使用的内存映射：
- `0x40000000`：ROM基地址
- `0x40004000`：代码段（对应ROM 0x4000）
- `0x40008000`：常量数据
- `0x40010000`：密钥存储（对应ROM 0xC000 或 0x10000?）
- `0x42000000`：加密数据区（对应ROM 0x1000）

## 完整逆向过程：字符串 "There_is_nothing_you_wanna_get.." 的提取

### 1. 定位验证函数

在字节码解释器 (0x4D00) 中，当遇到 `0xEE` 操作码时会调用地址 `0x4AB0` 的验证函数：

```
0x4ef4: call 0x4ab0    ; 调用验证函数
```

### 2. SPARC 立即数加载机制

SPARC 是 32 位 RISC 架构，单条指令只能编码有限的立即数位数。要加载一个完整的 32 位常量，需要使用 **sethi + or** 指令对：

```
sethi  imm22, %rd     ; 将 22 位立即数左移 10 位存入寄存器
                      ; %rd = imm22 << 10

or     %rd, simm13, %rd  ; 将低 13 位（实际用 10 位）或入寄存器
                         ; %rd = %rd | (simm13 & 0x3FF)
```

**组合效果**：`%rd = (imm22 << 10) | (simm13 & 0x3FF)` = 完整的 32 位值

### 3. 反汇编 0x4AB0 区域的指令

以下是从 ROM 偏移 0x4AB4 开始的指令序列：

```sparc
; === 第 1 组: "Ther" ===
0x4AB4: sethi 0x151a19, %r28   ; 指令: 0x39151a19
0x4AB8: or %r28, 0x172, %r28   ; 指令: 0xb8172172
; 计算: (0x151a19 << 10) | (0x172 & 0x3FF) = 0x54686572
; 0x54686572 (BE) = "Ther"

; === 第 2 组: "e_is" ===
0x4ABC: sethi 0x1957da, %r29   ; 指令: 0x3b1957da
0x4AC0: or %r29, 0x173, %r29   ; 指令: 0xba176173
; 计算: (0x1957da << 10) | (0x173 & 0x3FF) = 0x655f6973
; 0x655f6973 (BE) = "e_is"

; === 第 3 组: "_not" ===
0x4AC8: sethi 0x17db9b, %r28   ; 指令: 0x3917db9b
0x4ACC: or %r28, 0x374, %r28   ; 指令: 0xb8172374
; 计算: (0x17db9b << 10) | (0x374 & 0x3FF) = 0x5f6e6f74
; 0x5f6e6f74 (BE) = "_not"

; === 第 4 组: "hing" ===
0x4AD0: sethi 0x1a1a5b, %r29   ; 指令: 0x3b1a1a5b
0x4AD4: or %r29, 0x267, %r29   ; 指令: 0xba176267
; 计算: (0x1a1a5b << 10) | (0x267 & 0x3FF) = 0x68696e67
; 0x68696e67 (BE) = "hing"

; === 第 5 组: "_you" ===
0x4ADC: sethi 0x17de5b, %r28   ; 指令: 0x3917de5b
0x4AE0: or %r28, 0x375, %r28   ; 指令: 0xb8172375
; 计算: (0x17de5b << 10) | (0x375 & 0x3FF) = 0x5f796f75
; 0x5f796f75 (BE) = "_you"

; === 第 6 组: "_wan" ===
0x4AE4: sethi 0x17ddd8, %r29   ; 指令: 0x3b17ddd8
0x4AE8: or %r29, 0x16e, %r29   ; 指令: 0xba17616e
; 计算: (0x17ddd8 << 10) | (0x16e & 0x3FF) = 0x5f77616e
; 0x5f77616e (BE) = "_wan"

; === 第 7 组: "na_g" ===
0x4AF0: sethi 0x1b9857, %r28   ; 指令: 0x391b9857
0x4AF4: or %r28, 0x367, %r28   ; 指令: 0xb8172367
; 计算: (0x1b9857 << 10) | (0x367 & 0x3FF) = 0x6e615f67
; 0x6e615f67 (BE) = "na_g"

; === 第 8 组: "et.." ===
0x4AF8: sethi 0x195d0b, %r29   ; 指令: 0x3b195d0b
0x4AFC: or %r29, 0x22e, %r29   ; 指令: 0xba17622e
; 计算: (0x195d0b << 10) | (0x22e & 0x3FF) = 0x65742e2e
; 0x65742e2e (BE) = "et.."
```

### 4. 手工计算验证

以第一组 "Ther" 为例：

```
sethi 0x151a19, %r28
  imm22 = 0x151A19 = 0001 0101 0001 1010 0001 1001 (22 bits)
  左移 10 位: 0x54686400

or %r28, 0x172, %r28
  simm13 = 0x172 = 370 (decimal)
  取低 10 位: 0x172 & 0x3FF = 0x172

  结果: 0x54686400 | 0x172 = 0x54686572
```

将 `0x54686572` 按大端序解释为 ASCII：
- 0x54 = 'T'
- 0x68 = 'h'
- 0x65 = 'e'
- 0x72 = 'r'

→ **"Ther"**

### 5. 完整字符串重建

| 组号 | 指令偏移 | 计算值 | ASCII |
|------|----------|--------|-------|
| 1 | 0x4AB4 | 0x54686572 | Ther |
| 2 | 0x4ABC | 0x655f6973 | e_is |
| 3 | 0x4AC8 | 0x5f6e6f74 | _not |
| 4 | 0x4AD0 | 0x68696e67 | hing |

| 8 | 0x4AF8 | 0x65742e2e | et.. |

**拼接结果**: `There_is_nothing_you_wanna_get..`

### 6. 该字符串的用途

在验证函数中，这个字符串被存储到栈上（通过 `std` 指令存储双字），然后与另一组加密常量进行 XOR 比较：

```sparc
0x4AC4: std %r28, [%r30 + -168]   ; 存储 "Ther" + "e_is" 到栈
0x4AD8: std %r28, [%r30 + -160]   ; 存储 "_not" + "hing" 到栈
0x4AEC: std %r28, [%r30 + -152]   ; 存储 "_you" + "_wan" 到栈
0x4B00: std %r28, [%r30 + -144]   ; 存储 "na_g" + "et.." 到栈
```

这个字符串是验证用户输入正确性的密钥，也是题目的核心秘密。
